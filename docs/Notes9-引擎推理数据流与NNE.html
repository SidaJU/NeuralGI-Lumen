Notes 9：引擎推理数据流与 NNE

神经网络如何在 UE 渲染管线里跑起来 —— 从 ONNX 到屏幕 GI 的完整链路

1. NNE 是什么

NNE（Neural Network Engine）：UE 5.x 内置的神经网络推理框架 —— 把训练好的 ONNX 模型在引擎里（GPU 上）跑起来，并无缝嵌进渲染管线。

三个核心概念

概念是什么我们用的
NNEModelData 模型资产，从 .onnx 导入生成 /Game/model_nspf_dyn
Runtime（运行时） 真正执行推理的后端 NNERuntimeORTDml（ONNX Runtime + DirectML，≈1ms）
备选 NNERuntimeRDGHlsl（纯 HLSL，≈23ms）
IModelInstanceRDG 模型实例，负责把推理插入 RDG（渲染图） 每帧调用一次
关键点：我们用的是 RDG 接口（...RDG 后缀）—— 推理作为一个 GPU pass 插进渲染图，输入/输出都是 RDG buffer（显存），不回读 CPU。这正好和我们的 shader 无缝衔接。

2. ★ 推理数据流总览

3. 三段式逐步拆解

① InputProcess（特征构建）
用 compute shader NSPFFeatureBuild.usf：一个线程 = 一个 texel = 一个样本。
采样 5 张纹理（radiance / hitdist / depth / normal / wpos）→ 组装 52 维特征 → 写进 InputBuf。
为什么必须用 shader：NNE 的 RDG 接口不支持 CPU 上传数据（官方 NNEDenoiser 也一样）。
② NNE 推理
调用 Instance->EnqueueRDG(GraphBuilder, {InputBuf}, {OutputBuf})。
它只是把推理 pass 加入 RDG 图，GPU 执行时自动跑 —— 我们不用管同步、不用回读。
输入 (N,52) → 输出 (N,3)（log1p 域的 radiance）。
③ OutputProcess（写回）
用 compute shader NSPFWriteBack.usf：读 OutputBuf → exp(x)-1 还原到线性域 → 乘 DebugScale → 写进 NNRadiance 纹理。
该纹理随后覆盖 ScreenProbeRadiance。

6. 两个反直觉设计

① 为什么用 shader 写特征 buffer，而不是 CPU 上传？
NNE 的 RDG 接口不支持 CPU 数据上传，官方 NNEDenoiser 也只用 shader 写 buffer。
所以必须用 compute shader 把纹理采样 → 组装 52 维 → 写进 InputBuf。这是"三段式"存在的根本原因。
② 为什么 buffer 必须是 typed + NNE flag？ 
FRDGBufferDesc InDesc = CreateBufferDesc(sizeof(float), NumSamples * 52);
InDesc.Usage |= EBufferUsageFlags::NNE;                 // 官方写法
CreateUAV(FRDGBufferUAVDesc(InputBuf, PF_R32_FLOAT));   // 必须显式 Format
因为 NNE 内部的 Gemm 算子用 PF_R32_FLOAT 建 SRV —— 必须是 typed buffer（structured 会读到 0）。

8. Dispatch 全链路（怎么调度的）

整个链路有 3 个执行点：2 个是我们显式 dispatch 的 compute shader，中间 1 个由 NNE 内部接手。

顺序内容代码位置谁 dispatch
①特征构建 CSLumenScreenProbeNSPF.cpp:388-396我们显式 AddPass
②NNE 推理:410NNE 内部（我们不写 dispatch）
③写回 CS:441-446我们显式 AddPass

① 特征 CS 的 dispatch

FComputeShaderUtils::AddPass(
    GraphBuilder,
    RDG_EVENT_NAME("NSPF.BuildFeatures"),
    ERDGPassFlags::Compute | ERDGPassFlags::NeverCull,
    ComputeShader,
    PassParameters,
    FComputeShaderUtils::GetGroupCount(
        FIntVector(AtlasSize.X, AtlasSize.Y, 1),
        NSPF_GROUP_SIZE));

参数怎么算

量值
AtlasSize680 × 432
NSPF_GROUP_SIZE8
ThreadGroupCount(ceil(680/8), ceil(432/8), 1) = (85, 54, 1)
总线程数85 × 54 组 × 64 = 293,760（正好 = 样本数）
★ 为什么 NSPF_GROUP_SIZE = 8
因为 gather resolution = 8：每个 probe 在 atlas 里是 8×8 = 64 个方向格子。
线程组 numthreads(8,8,1) = 64 线程 → 一个线程组正好处理一个 probe 的 64 个方向格子。
组内 64 线程访问连续内存（同一 probe 的 64×52 个 float），缓存友好。

② NNE 推理（不写 dispatch）

const auto Status = Instance->EnqueueRDG(GraphBuilder, Inputs, Outputs);

NNE 内部把推理展开为若干 RDG pass（Gemm / ElementWise 等）， 由 NNE 自己决定各算子的 dispatch 参数；我们只提供 buffer binding。

③ 写回 CS 的 dispatch

同样 GetGroupCount((AtlasSize.X, AtlasSize.Y, 1), NSPF_GROUP_SIZE) = (85,54,1)； 每线程读 OutputBuf 的 3 个 float → exp(x)-1 → 写进 NNRadiance 的一个 texel。

passdispatch 参数线程总数每线程处理
BuildFeatures(85,54,1) × 8×8293,760写 52 维特征
NNE 推理NNE 内部—52 → 3
WriteBack(85,54,1) × 8×8293,760写 3 维 RGB
两个 CS 都有 NeverCull：与官方 NNEDenoiser 一致 —— 防止 RDG 因“输出未被直接引用”而误剔除 pass（我们的输出是给 NNE buffer 用的）。

9. Buffer 写入目标与零拷贝视图

一句话：BuildFeatures 把结果写进 InputBuf（GPU 显存 buffer）； NNE 推理读的就是这块 buffer —— 同一 GPU 资源：shader 用 UAV 写，NNE 用 tensor binding 读， 零拷贝、零回读。

三步绑定链

① 创建 buffer（:353-357） 
FRDGBufferDesc InDesc =
    CreateBufferDesc(sizeof(float), NumSamples * NSPF_IN_DIM);   // 293760 × 52
InDesc.Usage |= EBufferUsageFlags::NNE;
FRDGBufferRef InputBuf = GraphBuilder.CreateBuffer(InDesc, TEXT("NSPF.Features"));
② shader 以 UAV 写（:382-384） 
// C++：UAV 视图指向 InputBuf
PassParameters->OutputFeatureBuffer =
    GraphBuilder.CreateUAV(FRDGBufferUAVDesc(InputBuf, PF_R32_FLOAT));

// usf：RWBuffer<float> OutputFeatureBuffer;  每个线程写 52 个 float

shader 里的 OutputFeatureBuffer 就是 InputBuf 的 UAV 视图 —— 写进去 = 写进 InputBuf 的显存。

③ NNE 以 tensor binding 读（:400-403） 
UE::NNE::FTensorBindingRDG InBinding;
InBinding.Buffer = InputBuf;      // 同一个 InputBuf
Inputs.Add(InBinding);

NNE 把它当作形状 (293760, 52) 的 tensor 来读 —— 读的就是 shader 刚写进去的显存。

为什么零拷贝

环节视图操作
BuildFeatures CSRWBuffer<float>（UAV）写
NNE 推理tensor binding（底层 buffer 引用）读

两者指向同一个底层 GPU buffer —— 不是“写完再拷贝一份给 NNE”，而是 NNE 直接读那块显存。 RDG 自动保证 pass 顺序与依赖（BuildFeatures 先写 → NNE 后读），无需手动同步。

数据在 buffer 里的排布

[0........51] [52.......103] [104......155] ...
  样本0(52维)    样本1(52维)    样本2(52维)
  共 293760 × 52 = 15,275,520 个 float（约 61 MB）

shader 用 BufferOffset() 定位：(y*width + x) * 52； NNE 按 (293760, 52) 解释同一片内存 —— 排布一致，无需转换。

对称：OutputBuf 也一样

NNE 推理   → 写 OutputBuf（293760 × 3）
    ↓
WriteBack CS → 以 SRV 读同一块 OutputBuf（:433-434）
    ↓
expm1 还原   → 写进 NNRadiance 纹理
总结：整条链路 GPU buffer 只有一份 —— shader 和 NNE 是它的不同“视图” （UAV 写 / tensor binding 读 / SRV 读）。这是 RDG + NNE 集成高效的核心原因：无 CPU 回读、无 GPU 拷贝。
