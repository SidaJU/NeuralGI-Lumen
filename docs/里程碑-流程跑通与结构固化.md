# 里程碑：流程跑通与结构固化

> **本文件是一个界碑。**
>
> 它标记：项目的**工程结构已经跑通并基本固定**，接下来的重心从"能不能跑"转向"跑得好不好" —— 即**算法调优阶段**。
>
> 写于：三条通路（A / B' / B''）全部训练完成并对比之后。

---

## 0. 这次界碑意味着什么

| 之前 | 之后 |
|---|---|
| 每次推理临时拼参数，图命名混乱 | 枚举式入口，输出自动规范命名 |
| A / B' / B'' 概念混淆，甚至训错了都不知道 | 三条通路写进注册表，训练时会打印确认 |
| 关注"能不能采到 / 训起来" | 关注"怎么训得更准 / 泛化更好" |

**结构固定的含义**：目录、接口、数据格式、调用方式**不再频繁变动**。后续改动集中在算法层面（损失函数、模型容量、特征、训练策略）。

## 1. 已固化的结构

### 1.1 引擎侧

| 项 | 内容 |
|---|---|
| 文件 | `LumenScreenProbeDump.h/.cpp`（新增）、`LumenScreenProbeFiltering.cpp`（1 处调用）|
| 标记 | `[theozhu++]` / `[theozhu--]` |
| 产出 | 每帧 6 个 npy + 1 个 json + `meta.json` |
| 控制 CVar | `Enable` / `OutputDir` / `MaxFrames` / `WaitForMotion` |

### 1.2 数据格式（不再变）

| 项 | 值 |
|---|---|
| 特征维度 | **56**（27 邻域 radiance + 9 hitdist + 9 valid + 7 几何 + 3 历史 + 1 历史有效）|
| 每个 probe 方向格子 | `GatherRes² = 8×8 = 64` |
| 配对方式 | **相机矩阵最近邻**（不依赖帧号）|
| 归一化 | `log1p` / 反归一化 `expm1` |

### 1.3 三条通路（核心）

| 方案 | 模型 | 输入 → 答案 | 任务 |
|---|---|---|---|
| **A** | `runs/b_full` | low.in(64条未滤波) → **low.gt(64条已滤波)** | 纯滤波 |
| **B'** | `runs/b_prime_real` | low.in(64条未滤波) → **high.gt(256条已滤波)** | 滤波 + 补射线 |
| **B''** | `runs/b_rayonly` | low.in(64条未滤波) → **high.in(256条未滤波)** | 纯补射线 |

三者**输入完全相同**，只有答案来源不同 —— 这是刻意设计，便于公平对比。

### 1.4 推理入口（首选）

```bat
python tools\eval\run_infer.py --list
python tools\eval\run_infer.py --scheme B --scene train --frames 150
```

- `--scheme`：`A` / `B` / `B2`
- `--scene`：`train` / `new`

输出：`output/<场景>/<方案>_f<帧号>.png`，图内自带完整标注。

## 2. 已验证的结论（调优前的基线）

### 2.1 相机矩阵配对有效 ✅

两遍采集速度不同（low 1089 帧 vs high 99 帧），帧号彻底错位，但矩阵配对距离 **0.00e+00** —— 证明只要轨迹相同，采样密度不同也能完美配对。

> 这条结论让后续采集不必再纠结"两遍帧数是否一致"。

### 2.2 用 high 数据训练确实有效 ✅

| | A（没用 high）| B'（用了 high）| B''（用了 high）|
|---|---|---|---|
| train 输出平滑度 | 0.707 | **0.554** | 0.571 |
| new 输出平滑度 | 0.953 | **0.725** | 0.774 |

用 256 条数据训练的模型，输出质量明显优于只用 64 条的。

> 反证了之前那个 bug 的代价：白采集了高射线数据却没用上。

### 2.3 B' 是当前最优方案 🏆

在两个场景都输出最干净的结果，**B' 作为部署主力候选**。

### 2.4 模型普遍"过度平滑"

所有模型输出都比答案平滑（完成度 >100%），因为答案含随机噪点、不可预测，模型学到的是"平滑期望"。

**这对 GI 是好事**（噪点本就该去掉），但**风险是抹掉真实细节** —— 需要看图确认，也是调优的重点。

## 3. 已知问题（调优要解决的）

| # | 问题 | 影响 |
|---|---|---|
| 1 | **过度平滑**（输出比答案平滑 20%+）| 可能抹掉真实细节 |
| 2 | 泛化下降（new 场景完成度低于 train）| 换场景效果打折 |
| 3 | 完成度指标 >100% 不好解读 | 需要一个更合理的"质量标准" |
| 4 | S4 接回引擎未做 | 模型还没真正在 Lumen 里跑过 |
| 5 | 原始"降射线"目标不可达（引擎限制 Trace≥8）| 只能做到画质提升，非性能优化 |

## 4. 下一阶段：算法调优

### 4.1 调优方向（按推荐顺序）

#### ① 损失函数（优先）

当前用 relative L2，它鼓励"整体数值接近"，但不保护**边缘/细节**。

可尝试：
- 加**梯度保边项**（鼓励输出与 GT 的梯度一致，防止糊）
- 加**感知/结构项**（SSIM 类）
- 对暗部加权（GI 暗部噪点最明显）

#### ② 模型容量

当前 `hidden=64, layers=4`（16K 参数）。可试：
- `hidden=128`（参数 ~4 倍）
- `layers=5~6`

**权衡**：容量大 → 拟合好但推理慢（要守住 0.749ms 这条线附近）。

#### ③ 特征工程

56 维是否够？可考虑：
- 增加更大邻域（5×5）
- 加入 material / albedo 等辅助通道
- 改进时域特征（当前只用 1 帧历史，可试多帧）

#### ④ 数据

- **多场景混合训练**（当前只有 2 个场景）
- 数据增广（噪声扰动、亮度扰动）

#### ⑤ 训练策略

- epochs（当前 15，是否已收敛？）
- 学习率 / 调度
- 每帧采样数（8192）

---

### 4.2 评估标准（固定下来，便于横向对比）

每次调优后都跑同一套评估，记录数字：

```bat
:: 三方案 × 两场景，同一帧
python tools\eval\run_infer.py --scheme B --scene train --frames 150
python tools\eval\run_infer.py --scheme B --scene new   --frames 30

:: 数值评估
python eval/eval_smoothness.py <ckpt> D:/ProbeDump_B_low --gt-dir D:/ProbeDump_B_high --frames 8 --stride 11
```

记录这 5 个数：

| 指标 | 说明 |
|---|---|
| **完成度** | 补上"输入→答案"差距的比例 |
| **MSE 降低** | 相对恒等映射的改善 |
| **relL2 降低** | 同上（更看重相对误差）|
| **输出平滑度** | 越低越干净 |
| **推理耗时** | TensorRT 实测 |

同时**必须看图** —— 数字判断不了"细节有没有被抹掉"。

---

### 4.3 调优的流程建议

```
① 提出假设（比如"加梯度保边项能减少过度平滑"）
② 改一处（只改一处！）
③ 重训（15 epochs，约 10 分钟）
④ 跑固定评估，记录 5 个数字
⑤ 出图肉眼确认
⑥ 对比基线，决定保留还是回滚

基线（B'，当前）：
  train: in 0.836 -> out 0.554 (答案 0.690)
  new:   in 1.164 -> out 0.725 (答案 0.846)
```

**关键纪律：一次只改一个变量**，否则不知道是哪个改动起了作用。
