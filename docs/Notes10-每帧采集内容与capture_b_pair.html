Notes 10：每帧采集内容与 capture_b_pair 脚本

数据采集管线的两个问题：每帧落盘的 8 个文件是什么 / capture 脚本怎么一次采两遍并识别 Sequencer

1. 每帧采集的 8 个文件

引擎每渲染一帧（FilterScreenProbes 末尾触发 EnqueueDump），异步 readback 后落盘一组文件。以 probe 网格 90×35、gather=8（atlas 720×280）为例：

文件来源（引擎纹理/数据）形状用途
frame_%06d_in.npy CompositedScreenProbeRadiance (280, 720, 3) 训练输入：滤波前 radiance（64 射线，噪点大）
frame_%06d_gt.npy ScreenProbeRadiance (280, 720, 3) 训练答案：滤波后 radiance（干净）
frame_%06d_hitdist.npy ScreenProbeHitDistance (280, 720) 特征 [27:36]：射线命中距离（区分"远处天空"与"近处墙"）
frame_%06d_depth.npy ScreenProbeSceneDepth (35, 90) 特征 [45]：log 深度；也是有效过滤依据（depth≤0 → 该 probe 无效）
frame_%06d_normal.npy ScreenProbeWorldNormal (35, 90, 2) 特征 [46:48]：世界法线（八面体编码 2 通道）
frame_%06d_wpos.npy ScreenProbeTranslatedWorldPosition (35, 90, 4) 特征 [49:51]：世界坐标；方案 B 相机配对之外还用于历史重投影
frame_%06d.json View / Proj / PreViewTranslation — 相机矩阵：方案 B 两遍采集的配对依据（不依赖帧号）
meta.json 全局配置 — tracing/gather 分辨率、atlas 尺寸、probe 网格、downsample 等（每个目录只写一次）
训练时各文件的消费方式：
in → 特征 [0:27]（邻域 radiance，log1p 后）+ 残差基准 [12:15]；
gt → 训练目标（log1p 后）；hitdist → 特征 [27:36]；
depth/normal/wpos → 特征 [45:52] + 有效过滤；json → 方案 B 相机配对。

3. capture_b_pair.py 是什么、解决什么问题

位置：tools/capture/capture_b_pair.py（在 UE 编辑器的 Python 控制台里运行，不是命令行）。

它解决的问题：编辑器视口（非 PIE）不遵守 Project Settings 的"Use Fixed Frame Rate"。 实时播放 Sequencer 时，低射线（64 条）跑得快、高射线（256 条）跑得慢 —— 同样"第 N 帧"，两遍的相机位置完全不同 → 数据无法配对。

解法：不实时播放，而是把 Sequencer 播放头逐帧推（每推一帧等若干渲染帧）。 相机位置完全由帧号决定，与快慢无关 → 两遍严格对齐。

为什么用异步 tick 而不是 sleep

编辑器 Python 跑在主线程，time.sleep 会卡死渲染（根本不采集）。所以用 unreal.register_slate_post_tick_callback 注册每帧回调，异步推进状态机。

4. ★ 一次运行采两遍（不是一次一遍）

capture_b_pair.run() 一次调用 = 自动完成两遍采集： 先采 low（输入），自动切 CVar 后再采 high（答案），全程无需手动干预。

两遍的 CVar 差异（脚本自动设）

CVar第 1 遍 low第 2 遍 high
TracingOctahedronResolution8（64 条射线）16（256 条射线）
GatherOctahedronResolutionScale1.0 → Gather=80.5 → Gather=8（锁定）
ScreenProbeDump.OutputDir<prefix>_low<prefix>_high
MaxFrames都是 num_frames × hold（两遍相同）

Gather 都是 8 → atlas 形状一致 → 才能配对训练（这是方案 B 的核心约束）。

5. 怎么识别 / 驱动你的 Sequencer

脚本通过 unreal.LevelSequenceEditorBlueprintLibrary（Sequencer 编辑器的 Python API）操作：

① 找到序列（两种 getter 依次尝试）

lib = unreal.LevelSequenceEditorBlueprintLibrary
seq = lib.get_current_level_sequence()        # 先试这个
# 失败再试: lib.get_focused_level_sequence()
前提：Sequencer 面板必须打开并载入了你的序列（它认的是"编辑器当前焦点"的序列）。 面板没打开 → 找不到序列 → 探测不到路径长度。

② 探测路径长度（用于自动铺满）

start = seq.get_playback_start()      # 帧号版
end   = seq.get_playback_end()
# 如果拿到的是 seconds 版本（get_playback_start_seconds），×60 换算成帧
length = end - start

③ 推进播放头（逐帧步进的核心）

lib.set_current_time(int(frame))      # ★ UE5.6 签名是 int 帧号
# 传 unreal.FrameNumber 对象会报错（我们踩过）

自动铺满逻辑

你只给 num_frames（要多少个采样点），脚本自动算间隔：
frame_step = 路径长度 // num_frames → 采样点等间隔铺满整条路径
例：路径 600 帧、要 40 个点 → step=15，采样点 0/15/30/.../585
（外加钳制：采样点不会越过路径末尾）

6. run() 的关键参数

capture_b_pair.run(num_frames=60, hold=10, seq_length=600, out_prefix="D:/ProbeDump_X")
参数含义注意
num_frames采样点数（不同相机位置）决定数据多样性
hold每个位置停几个渲染帧两遍自动相同（映射一致的关键）；太小会采到旧画面
frame_step采样点间隔（0=自动铺满）自动 = 路径长度 ÷ num_frames
seq_length路径总长（0=自动探测）探测失败时手动指定
out_prefix输出前缀写 <prefix>_low/_high；换场景必改，防覆盖
落盘帧数 = num_frames × hold（每个位置重复 hold 帧）

其他控制：capture_b_pair.stop() 中止；r.AntiAliasingMethod 0 由脚本自动设（关 TSR jitter）。

7. 内部状态机（异步推进）

8. ★ 完整踩坑故事：两遍为什么对不上，怎么解决的

背景：为什么需要“两遍配对”

方案 B：同一个相机位置，采两种质量的探针：

第 1 遍 low  ：64 条射线   → in.npy（噪点大，做输入）
第 2 遍 high ：256 条射线  → gt.npy（很干净，做答案）
配对的隐含前提：两遍的“第 N 帧”必须是同一个相机位置。
否则 in[帧N] 是“在 A 点看到的”，gt[帧N] 是“在 B 点看到的” → 网络学的是“从 A 点输入预测 B 点输出” = 纯噪声。

遇到的问题：两遍对不上（两层根因叠加）

最初做法是实时播放 Sequencer（点 Play），引擎按渲染帧自动 dump。问题立刻暴露：

根因说明
A. 两遍渲染帧率不同 实时播放时相机位置由真实时间决定，但采集按渲染帧计数 —— 同样叫“第 N 帧”，两遍对应的相机位置不同
B. 编辑器不遵守 Fixed Frame Rate 我们试过 Project Settings 里开 Use Fixed Frame Rate = 60 —— 该设置只对 PIE / 游戏运行生效，编辑器视口（非 PIE）不遵守，白设了

具体数字（路径总长 10 秒的示意）：

遍射线渲染帧率真实 5 秒时
low64 条~30 fps已采到 ~150 帧，相机在路径 50%
high256 条~10 fps才采到 ~50 帧，相机在路径 17%

（这就是脚本 docstring 里“60% / 30%”那个例子的含义：同样帧号，相机位置不同。）

更糟的是：渲染耗时逐帧波动（负载不均）→ 速度比例不是常数 → 连“事后按偏移量对齐”都做不到（diag_frame_offset.py 搜遍所有偏移 k，没有一个能让偏差归零）。

解法对比：实时播放 vs 逐帧步进

最终解法：三层防线

① 脚本逐帧步进（根治）
不实时播放，播放头由脚本一帧一帧推（set_seq_frame(i) → 等 hold 个渲染帧 → 采）。 相机位置完全由帧号决定，与渲染快慢无关 → 两遍天然对齐。
② 引擎侧 WaitForMotion（消除人的延迟）
逐帧步进解决了“速度”，但还有“手动按 Enable 与 Play 的时间差”问题。 引擎在 Enable 后不立即计数，等检测到相机真正开始运动才从 frame_000000 起算 → 两遍起点都是“相机刚起步那一刻”，与你的手速无关。
③ 相机矩阵配对（兜底）
即便如此，渲染帧计数仍可能有微小粒度差异。最后兜底：不按帧号配对，按相机矩阵最近邻配对 —— 每帧记录 View/Proj 矩阵，在另一遍里找矩阵最接近的帧。

实测结果

阶段相机矩阵匹配距离配对状态
修复前（实时播放）偏差数千❌ 全错
修复后（逐帧步进 + 矩阵配对）0.00e+00✅ 1195 帧全部完美配对
教训（通用思路）：按渲染帧计数的采集，天然对渲染速度敏感 —— 只要两遍渲染成本不同，帧号就不可靠。

解法优先级：
① 让位置由帧号决定（逐帧步进）→ ② 让起点由事件决定（WaitForMotion）→ ③ 兜底按内容配对（相机矩阵）。

这套“时间无关采集”思路适用于任何要采两遍不同开销渲染结果并配对的场景，不局限于 Lumen。
