# S4：引擎接入技术方案（调研结论）

> 目标：把训练好的模型接入 UE，实时替换 Lumen 的 Screen Probe 滤波。
> 本文记录**技术选型调研**，结论是：**优先用 UE 原生的 NNE + NNERuntimeRDG，而不是直接接 TensorRT**。

---

## 0. 一句话结论

> **不需要自己接 TensorRT。** UE 自带 `NNERuntimeRDG` 插件，用 RDG 实现 NNE（Neural Network Engine）推理，已支持 ONNX 的 **Gemm**（全连接层）—— 我们的 4 层 MLP 完全可跑。
> 这条路纯 UE 原生、**不需要 CUDA 工具包**、天然与 RDG 集成，工程量远小于直连 TensorRT。

---

## 1. 关键发现（本地调研）

### 1.1 ✅ 引擎自带 NNERuntimeRDG

```
Engine/Plugins/Experimental/NNERuntimeRDG/NNERuntimeRDG.uplugin
```

官方描述：

> "A runtime implementing the Neural Network Engine (NNE) API, using the Render Dependency Graph (RDG)."

**用 RDG 实现 NNE** —— 与 Lumen 的渲染管线天然一致。

模块构成：

| 模块 | 类型 | 作用 |
|---|---|---|
| `NNEHlslShaders` | RuntimeAndProgram | HLSL 算子 shader |
| `NNERuntimeRDG` | Runtime | 运行时（展开模型到 RDG）|
| `NNERuntimeRDGData` | Runtime | 张量/属性数据 |
| `NNERuntimeRDGUtils` | Editor | ONNX → NNE 转换工具 |

### 1.2 ✅ 支持我们模型需要的算子

`NNERuntimeRDG/Private/Hlsl/NNERuntimeRDGGemm.cpp`：

```cpp
Registry.OpAdd({{TEXT("Gemm"), TEXT("Onnx")}, 7},  ...);
Registry.OpAdd({{TEXT("Gemm"), TEXT("Onnx")}, 9},  ...);
Registry.OpAdd({{TEXT("Gemm"), TEXT("Onnx")}, 11}, ...);
Registry.OpAdd({{TEXT("Gemm"), TEXT("Onnx")}, 13}, ...);
```

- **Gemm** = ONNX 的全连接层算子（`nn.Linear` 导出即 Gemm）→ 我们的 MLP 直接可用
- 另有 `MatMul`、`Conv` 等算子

### 1.3 ⚠️ 没有 DLSS / NGX / Streamline

`Engine/Plugins/Runtime/Nvidia/` 只有：
- `GeForceNOWWrapper`（云游戏，无关）
- `Reflex`（低延迟，无关）

NVIDIA 的 DLSS/Streamline 是**单独分发**的，不在开源源码里。但这不影响我们 —— 我们不需要它们。

### 1.4 ⚠️ CUDA 版本不匹配（TensorRT 路线的障碍）

| 项 | 版本 |
|---|---|
| 系统 CUDA Toolkit | **v12.8** |
| 已下载的 TensorRT | `TensorRT-10.16.1.11.Windows.amd64.cuda-**12.9**` |

直连 TensorRT 需要先装 CUDA 12.9 或换匹配 12.8 的 TensorRT 版本。

**NNE RDG 路线完全绕开这个问题**（不依赖 CUDA 工具包）。

### 1.5 ✅ 项目里有 CUDA 经验（备用）

```
RaidGame/Tools/MeshChecker/kernel.cu
RaidGame/Tools/MeshChecker/MeshChecker.vcxproj
```

- 独立的 VS CUDA 项目，用 `CUDA 12.6.props/targets`，链接 `cudart_static.lib`
- 说明团队有人做过 CUDA，若将来切 TensorRT 路线有经验基础

### 1.6 📄 外部参考：NVIDIA 官方 NNE + TensorRT 集成

2026 年 4 月 30 日 NVIDIA 开发者博客宣布 **TensorRT for RTX Runtime 的 Unreal Engine NNE 集成**。

意义：
- NNE 是 UE 官方推理框架，**NVIDIA 正在为其提供 TensorRT 后端**
- 意味着：**先用 NNE 通用后端跑通，以后可无缝切 TensorRT 加速，API 不变**

## 2. 技术选型对比

| 维度 | TensorRT C++ 直连 | **NNE + NNERuntimeRDG** ⭐ |
|---|---|---|
| 集成难度 | 高（CUDA 上下文、DX12↔CUDA 互操作、构建系统）| **中**（UE 原生插件）|
| CUDA 依赖 | 需要（且版本要匹配）| **不需要** |
| 与 RDG 集成 | 需手工桥接 | **原生**（就是 RDG）|
| 硬件锁定 | NVIDIA | **不锁** |
| 极致性能 | TensorCore/FP16/INT8 | 略低（HLSL 展开，无 TensorCore）|
| 后续升级 | — | 可切 NVIDIA 的 NNE+TensorRT 后端 |

**结论**：我们的模型只有 16K 参数，NNE RDG 的性能足够；优先选简单路线。

---

## 3. 推荐实施路线

### S4.0 — 环境准备与模型转换（0.5 天）

1. 在 `RaidGame.uproject` 启用插件：
   - `NNERuntimeRDG`（及其依赖：NNE、NNEHlslShaders 等）
2. 用编辑器（NNERuntimeRDGUtils）把 `model.onnx` 导入为 `.nne` 资产

### S4.1 — 推理跑通 + 一致性验证（1~2 天）★先做这个

写一个最小测试（控制台命令或 Editor 模块）：

1. 加载 `.nne` 模型，创建实例
2. 喂**真实数据**：用我们采集的 56 维特征（Python 侧导出一份 npy）
3. 跑推理
4. **与 Python 的 `torch` 输出逐元素对比**（误差应 < 1e-3）
5. 测单次推理耗时

> 这一步验证"NNE 能跑我们的模型且数值正确"，是后续一切的前提。

### S4.2 — 特征构建 GPU 化（最大工作量）

把 `probe_dataset._build_features` 的逻辑翻译成 compute shader（HLSL）：
- 3×3 邻域采样（同方向跨 probe）
- hitdist / valid 邻域
- 几何（log 深度、法线、相对坐标）
- 时域重投影（历史帧）

验证：shader 输出的 56 维 vs numpy 输出一致。

### S4.3 — 接入 Lumen

在 `FilterScreenProbes` 里：
1. 特征 compute shader → RDG buffer
2. NNE 推理（RDG）
3. 输出写回 `ScreenProbeRadiance`

用 CVar 开关切换「Lumen 传统滤波 / NN 滤波」，同屏 A/B 对比画质与耗时。

## 4. 风险与备选

| 风险 | 应对 |
|---|---|
| NNERuntimeRDG 是 Experimental，可能有坑 | S4.1 先验证；不行则换 ONNX Runtime 或回退 TensorRT |
| 特征 shader 化工作量大 | 分算子逐个翻译 + 逐个验证 |
| 推理耗时超预算 | 切 NVIDIA 的 NNE+TensorRT 后端（API 不变）|
| 内存：94,656 texel × 56 维 FP32 ≈ 21MB/帧 | 可接受；必要时改 FP16 |
